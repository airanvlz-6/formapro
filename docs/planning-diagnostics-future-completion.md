# Planning diagnostics + future completion guard

Base auditada: `7a1c5e4276870ee48a64847294c266f99df5b531`.

1. **Origen.** `generateContractSession` registra el resultado de cada llamada al proveedor, del parser/shape, del validator individual y de duplicación. No se añade un segundo validador ni se cambia el schema. Los subgrupos de dosis, suficiencia y presupuesto se identifican desde las violations del validador real.
2. **Attempt.** `SESSION_BUILDER_ATTEMPT` contiene planningRunId, builderInvocationId, hash de identidad del contrato, semana, día, attempt/maxAttempts, stage, result/code, violations seguras, retryEligible/retryReason y detalles del fallo. El ID de generación se crea en servidor y viaja en el contexto firmado existente; nunca se registra el token. Fuera del flujo semanal o con un token anterior, el run ID puede ser null y permanece la identidad de invocación.
3. **Retry.** Se mantienen dos intentos máximos y las condiciones anteriores, con el mismo prompt. JSON/shape genérico termina en el primero; DOSE de parseo permite el segundo; los prefijos existentes de contrato y duplicación mantienen sus reglas. El resumen final incluye attemptCount, finalStage, finalViolations y retryExhausted, también al fallar. Preflight sin llamada al modelo mantiene su respuesta previa.
4. **Privacidad.** No se registran prompt, respuesta completa, HMAC, usuario ni contexto del atleta. Los códigos se conservan; sufijos que puedan contener texto arbitrario se omiten, preservando campos numéricos de dosis e índices seguros. EXPECTED/RECEIVED quedan unknown cuando el validator no devuelve esos detalles. Los metadatos del proveedor se limitan a stopReason, outputTokens, número/tipos de bloques, longitud, respuesta vacía e indicador max_tokens; no conceden aceptación. Cada intento limpia sus metadatos, incluso si falla el siguiente request.
5. **Orchestrator.** El resultado por día muestra intentos, etapa, violations seguras y agotamiento. El aborto registra únicamente code/diagnostics. El log de calendario identifica siete slots; otro log cuenta los targets reales. Sigue intacto el retorno null antes de guardar si cualquier Builder es inadmisible.
6. **Preservación.** `ORCHESTRATOR_PRESERVATION` separa completedDays de protectedDays (pueden solaparse). Describe cada slot mediante día, fecha derivada, completed, weeklyProtected, protectionReason y slotStatus. La proyección del cliente sirve solo para diagnóstico y no decide autoridad.
7. **Estrategia.** `WEEKLY_STRATEGY_DIAGNOSTIC` se emite después de seleccionar opciones del contrato canónico: fase/objetivo, PRIMARY/SUPPORTING/MAINTENANCE, adaptaciones diferidas y daily intents con role/adaptation/method. Referencias de debilidades que no sean IDs del catálogo se resumen como unknown. Los slots fijos sin intent en su opción se muestran como protegidos con campos null; no se inventan adaptaciones a partir del texto almacenado. preferredAdaptations vacío no elimina las adaptaciones canónicas.
8. **Invariant.** En preparación semanal se deriva la fecha desde targetWeekStart + día. Si completada es exactamente true y la fecha supera today canónico, se devuelve WEEKLY_CONTEXT_INVALID / FUTURE_COMPLETION_NOT_ALLOWED y diagnóstico seguro. No se llama al Planner ni se modifica el snapshot rechazado. El flujo HTTP obtiene today mediante la autoridad temporal canaria existente.
9. **Escritura.** `recordPlanCompletion` compara la fecha efectiva normalizada con hoy en Atlantic/Canary, antes de leer/escribir el plan. Una fecha futura devuelve FUTURE_COMPLETION_NOT_ALLOWED. Una fecha civil de hoy o anterior conserva la política de admisión existente. La aritmética UTC no implica usar el timezone del proceso.
10. **Legacy.** No se barren ni corrigen filas. Un snapshot con completion futura detiene la generación de forma explícita; el plan almacenado permanece intacto. REST/RECOVERY/UNAVAILABLE futuros con completada false conservan su protección. El cierre de semana no se modifica. La identidad por usuario/semana exactos mantiene aislado el historial de otra semana.
