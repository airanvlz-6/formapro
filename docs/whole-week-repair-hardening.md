# FORGE 3D.1 — Orquestación acotada de reparación

Auditoría previa sobre `dfab2af1bc76cc08a612560b4621d1171b6fe12c`:

```text
CURRENT_REPAIR_PIPELINE = validateAdmittedWholeWeek → si repair_required, elegir un target → repairSessionWithinReceipt → revalidar → guard final → INSERT/CAS
CURRENT_FAILURE_BEHAVIOR = invalid sin reparación, o reparación insuficiente, devuelve fallo; no escribe la candidata
CURRENT_PREVIOUS_PLAN_BEHAVIOR = snapshot de generación conservado; no delete ni update antes de aceptación final; el plan persistido previo permanece
CURRENT_USER_VISIBLE_FAILURE = API devolvía diagnóstico/razón y HTTP 422; apiCall reintentaba no-2xx hasta tres veces, terminaba como error de conexión; Orchestrator recargaba el plan y el caller mostraba un mensaje genérico invitando a volver a generar
```

Se inspeccionaron `enforceWholeWeek`, ambos módulos de validación/adaptación, Session Authority, Weekly Calendar Authority, receipts, generación individual, guardado, admisión de identidad, CAS y callers Web. El builder individual admite dos intentos internos; el helper de reparación no los tiene. La ruta preparaba efectos de ciclo/outcome en memoria, pero sus escrituras solo ocurrían después del commit del plan. No se consultaron datos personales ni se ejecutaron pruebas de producción.

## Informe solicitado

1. **Pipeline anterior.** El listado anterior refleja el código leído, no una inferencia desde el informe 3D. La autoridad final ya era determinista.
2. **Límite anterior.** Una sesión, una propuesta y una llamada al modelo; selección por orden inverso de IDs implicados.
3. **Fallo evitable.** Dos errores independientes no podían corregirse juntos. Además, coverage missing llegaba como invalid con IDs vacíos y no entraba al intento, aunque pudiera haber un intent compatible. HTTP 422 introducía reintentos de transporte no contemplados en el presupuesto.
4. **Pipeline final.** Validación → resolución de targets → fase local → revalidación → resolución de errores residuales → como máximo una fase targeted → revalidación final → calendario/freshness/mutación existentes → última validación del candidato → receipt → persistencia. Si no hay ERROR no se llama al modelo.
5. **Clasificación.** `resolveWeekRepairPlan` separa errores reparables, no reparables y grupos por target. Warnings e información no crean targets. Los códigos de cobertura solo se consideran reparables cuando un contrato individual autenticado tiene intent de adaptación compatible con el grupo requerido o goal explícito.
6. **Selección.** Búsqueda exacta pequeña sobre hasta siete plazas: menor conjunto que interseca todos los grupos de errores. Desempates: menor coste de roles existentes, reutilización de targets ya implicados y orden estable de índices. PRIMARY se preserva frente a SUPPORTING/MAINTENANCE cuando el tamaño mínimo lo permite. Cada sesión recibe todos sus diagnósticos en una sola solicitud por fase.
7. **Máximo de targets.** Tres sesiones distintas entre ambas fases, no tres nuevas en cada una. Una fase local y una targeted; hasta seis intentos de propuesta en total. Límite y stages quedan en la traza serializable.
8. **Justificación.** El calendario existente tiene siete plazas; el caso solicitado de cuatro copias idénticas requiere modificar tres para conservar un ancla. Tres permite ese caso y el de dos errores independientes, sin admitir una regeneración indiscriminada de siete plazas. El presupuesto no es una regla deportiva. Si el conjunto mínimo excede tres se rechaza antes de gastar llamadas o aplicar un subconjunto provisional.
9. **Local repair.** Cada target se procesa una vez con su contrato original, intent, restricciones, referencias, suficiencia, presupuesto, estrategia firmada, diagnósticos y resúmenes estructurados de siblings. Las propuestas aceptadas se acumulan solo en memoria. Se conserva el helper de autoridad existente; la selección es determinista, la propuesta puede venir del modelo.
10. **Targeted regeneration.** Se calcula un nuevo conjunto mínimo únicamente desde los ERROR residuales. El prompt pide una composición alternativa tras el fallo local, dentro del mismo contrato. Una sesión corregida que ya no está implicada no se vuelve a generar.
11. **Máximo de fases.** El array finito `['local','targeted']` es la única secuencia; `targetedRegenerationCount` es cero o uno y `targetedSessionCount` cuenta sus targets.
12. **Sin loops.** No recursión ni llamadas al Planner/builder con retry interno. Cada helper hace una única solicitud; los fallos se registran por ID sin persistir texto de excepciones. Web hace como máximo una solicitud de guardado, también ante fallo de red.
13. **Sin regeneración total ciega.** Solo entran IDs que cubren ERROR explícitos o una cobertura ausente mapeada a un intent autenticado. El presupuesto de IDs distintos es compartido. REST, disponibilidad y frecuencia no se alteran.
14. **Daily Intent.** `verifiedRepairContract` autentica el receipt original antes de admitir un candidato. El helper conserva íntegro el contrato y solo reemplaza su proposal tras `validateSessionAgainstTrainingContract`.
15. **Weekly Strategy.** Se lee desde el receipt semanal verificado. Se proporciona al modelo como contexto firmado y no se modifica para aprobar una candidata.
16. **PRIMARY.** Tiene preferencia de conservación en empates, pero puede ser target si es la única vía compatible para materializar la adaptación. El validator mantiene sus ERROR de cobertura. No se declara cubierta por el mero hecho de intentar repararla.
17. **Scope.** No cambia disciplina ni pools. Las pruebas reales rechazan propuestas de otra modalidad, de equipo no permitido y de movimientos incompatibles.
18. **Availability.** El día procede del contrato original y el renderer lo conserva. No hay operación de traslado, añadido o eliminación de sesiones. Continúa la revalidación del calendario después de reparaciones.
19. **Restrictions.** Siguen pasando validación individual y freshness antes de persistir. Cambios durante las llamadas invalidan el guardado mediante los guards existentes; no se refresca una autoridad para ampliar silenciosamente sus permisos.
20. **Sufficiency.** Se conservan referencias, equipo/capacidades, límites y contexto de dosis. No se obtienen HR, ritmo, porcentajes o kg desconocidos del texto del modelo. Se mantiene toda la regresión 3C/3C.1.
21. **Receipts.** Cada propuesta modificada recibe un nuevo receipt de sesión, firmado mediante la autoridad existente. Se añade al receipt semanal final un resumen limitado: localRepairCount, targetedRegenerationCount, affectedSessionIds y finalStatus.
22. **Digests.** El digest semanal se calcula sobre `validationResult.candidate.sessions`, con la identidad final admitida. No sobre la candidata inicial. La prueba de CAS compara explícitamente el digest del receipt con las sesiones finalmente devueltas.
23. **Validación final.** Se conserva el validator 3D sin cambiar severidades, reglas ni semántica de warnings. Se ejecuta tras cada fase y otra vez al terminar; la ruta mantiene su última comprobación antes de INSERT/CAS.
24. **Persistence gating.** El helper de orquestación no recibe BD ni escribe. Los efectos de plan/log/event/cycle/outcome siguen después de la aceptación; no hay eventos provisionales ni receipt de éxito para una semana rechazada.
25. **Plan válido previo.** Prueba con Planner, builders, receipts, guardado real de la ruta y repositorio de prueba: se crea una semana válida, se propone otra sobre su snapshot y se agotan las dos fases. Fila y revisión anteriores permanecen exactamente iguales y hay cero escrituras nuevas. El caso exitoso usa UPDATE/CAS e incrementa la revisión una vez.
26. **Guardado parcial.** Las modificaciones locales viven en copias separadas de rows/sources. Si queda ERROR, la respuesta interna no devuelve una candidata aceptada ni sesiones para persistir. La unidad de escritura sigue siendo la semana final completa.
27. **API failure.** Se reutilizan `WEEK_COHERENCE_INVALID`, `WEEK_REPAIR_FAILED` y `WEEK_FINAL_VALIDATION_FAILED`. `wholeWeekFailure` entrega HTTP 200 con ok false, retryable false, planningStatus `could_not_build_valid_week` y mensaje fijo. No expone dump de validator, prompts, respuestas del modelo, HMAC ni stack. Códigos inesperados se proyectan al fallo controlado. Los guards previos de calendario/freshness conservan sus códigos existentes.
28. **Usuario.** Orchestrator sigue devolviendo null ante fallo y recargando el plan almacenado. Los callers de Focus/chat muestran un único mensaje de no confirmación de semana nueva, mencionando el plan previo si existe y revisión antes de otra generación. No declaran éxito ni rollback ante una escritura de resultado incierto. `apiCall` no repite guardar_plan_semana automáticamente.
29. **Warnings.** Mantienen su comportamiento 3D: semana pass con warnings puede persistir. Near duplicate, concentración o repetición intencional no disparan reparación solos.
30. **External unknown.** Se preserva el contexto 3D sin inventar patrones. No añade targets desde datos externos desconocidos o snapshots ambiguos.
31. **Mismo día.** No se inventa orden intradía; ese diagnóstico sigue siendo warning. La selección estable de IDs es una regla de orquestación, no una afirmación sobre secuencia de entrenamiento.
32. **Push/chest fixture.** Cuatro propuestas idénticas con `bench_press`/`horizontal_push`: el validator marca copias estructurales y concentración; el resolver conserva un ancla y cambia tres propuestas, dentro de sus contratos. La concentración informativa permanece después de pasar. No existe rama chest ni límite universal de cuatro exposiciones.
33. **RDL fixture.** `rdl` con adaptación/estímulo de cadena posterior: dos propuestas iguales requieren cambiar una. Se comprueba igualdad completa del contrato antes/después y cambio del receipt de la propuesta.
34. **Multi-error fixture.** Prueba del orquestador de producción con validator 3D real sobre hechos normalizados: duplicación y PRIMARY ausente requieren dos targets; ambos se resuelven sin targeted, sin cambiar el ancla. Los seams de autenticación/propuesta están aislados en esa prueba; las pruebas de HMAC y ruta real verifican por separado la autoridad individual.
35. **Objective missing.** El resolver mapea grupos de cobertura sin sessionIds a intents compatibles autenticados y rechaza protegidos, no autorizados o adaptación distinta. Algunas composiciones que incumplen el intent ya son rechazadas por 3C antes de llegar a 3D: no se relaja ese guard ni se afirma que el fixture normalizado atraviese una admisión individual inválida en producción. La nueva clasificación cubre faltantes que sí lleguen al boundary semanal con autoridad compatible.
36. **Éxito local.** Conteos observables: targets locales necesarios y targetedRegenerationCount cero; warnings residuales permiten pass.
37. **Éxito targeted.** Propuesta local insuficiente → una composición alternativa en targeted → pass. Pruebas con receipts reales y con ruta/CAS; solo se vuelve a proponer el target residual.
38. **Fallo targeted.** Copia sin corregir o propuesta fuera del contrato tras ambas fases → WEEK_REPAIR_FAILED, dos fases como máximo, no guardado. No se filtra la excepción del helper.
39. **Límite.** Cuatro errores independientes con cuatro targets mínimos producen limitExceeded y conjunto vacío. No se intenta reparar tres para después salvar parcialmente. El mismo presupuesto de tres IDs distintos se aplica al conjunto residual.
40. **Plan previo fixture.** La prueba de ruta existente se amplía para capturar el snapshot real al regenerar, verificar revisión inalterada tras fallo y revisión +1 mediante CAS tras éxito targeted.
41. **Sin regeneración ciega fixture.** Counters registran únicamente los dos IDs implicados en el caso multi-error; en targeted queda solo el error no resuelto. Las sesiones pass y las ya corregidas permanecen sin nuevas llamadas.
42. **Cross-domain.** El resolver usa roles, IDs, cobertura e intents; ninguna rama por nombre de deporte. Se mantienen fixtures 3D powerlifting-like, cycling-like, híbrido y calisthenics-like y el gate previo.
43. **Mobile-ready.** Módulos server/pure con DTOs JSON. Contadores, clasificación y traces serializan sin SDK/UI/DOM. Web y Expo reciben la misma autoridad del backend; no se implementa UI móvil.
44. **Tests.** Suites de orquestación, fallos/transporte, receipts, reparación, guardado, autoridad semanal y toda `lib/**/*.test.mjs`: **1167/1167 PASS**, 20 pruebas nuevas respecto a 3D, cero fallos y cero omitidas.
